## Сборка и запуск

Требуются JDK 17+, Maven 3.9+ и PostgreSQL. Для Payara Micro используйте JDK 17
или 21. Все команды ниже выполняются из корня репозитория.

Настройте подключение к своей БД (переменные используются и Flyway, и Payara):

```bash
export DB_HOST=localhost
export DB_PORT=5432
export DB_NAME=routes
export DB_USER=routes
export DB_PASSWORD='ваш-пароль'
export DB_SCHEMA=public
export DB_SSLMODE=disable
```

Для удалённого сервера задайте соответствующий `DB_SSLMODE` (например,
`verify-full` при настроенных сертификатах). База и роль должны существовать;
роль должна иметь права на создание объектов в указанной схеме.

Для новой пустой схемы:

```bash
mvn flyway:migrate
mvn flyway:validate flyway:info
mvn clean verify
java -jar target/payara-micro.jar --deploy target/routes.war --port 8080
```

Приложение: <http://localhost:8080/routes/>.

Миграции запускаются **до** развёртывания WAR: Hibernate проверяет готовую схему
при инициализации (`hibernate.hbm2ddl.auto=validate`). Обычная сборка и unit-тесты
не подключаются к БД. После каждого обновления сначала выполняйте
`mvn flyway:migrate`, затем развёртывайте приложение.

## Переход с существующей базы

Если таблицы уже созданы старым `db/schema.sql`, сначала сделайте резервную
копию и проверьте, что структура соответствует `V1__create_schema.sql`.
Для такой базы один раз выполните:

```bash
mvn flyway:baseline -Dflyway.baselineVersion=1
mvn flyway:migrate
mvn flyway:validate flyway:info
```

Baseline отмечает существующую схему как версию 1, без повторного создания таблиц
и удаления данных. Версия 2 устанавливает функции через `CREATE OR REPLACE`,
поэтому подходит и для базы, где старый `db/functions.sql` уже был выполнен.
Не выполняйте baseline для пустой или частично созданной схемы, а также повторно
после перехода на Flyway. Автоматический baseline отключён: непустая схема без
истории миграций требует этого явного шага. Команда `flyway:clean` отключена.

Применённые миграции не редактируйте: для изменения схемы или функций добавляйте
новые файлы `V3__description.sql`, `V4__description.sql` и т. д. При повторном
`migrate` уже применённые версии не исполняются заново, а их контрольные суммы
проверяются. Подробности: [Maven-плагин Flyway](https://documentation.red-gate.com/flyway/reference/usage/maven-goal),
[baseline](https://documentation.red-gate.com/flyway/reference/commands/baseline).

## Обработка ошибок и проверка

API сохраняет формат `{"message": "...", "fields": {}}`. Для неверных полей
`fields` содержит сообщения по именам полей. Именованные бизнес-исключения
обрабатываются отдельными JAX-RS mapper-ами: неверный ввод — 400, отсутствие
объекта — 404, конфликт — 409, отсутствие авторизации — 401. Отдельные mapper-ы
обрабатывают Bean Validation, JSON и HTTP-ошибки; `JsonRequestInterceptor`
нормализует обёртку JSON-B, которую Jersey создаёт при чтении запроса.
HTTP-заголовки, например
`Allow`, сохраняются. Ошибки проверки возвращаемого значения — 500.

`ServiceErrorInterceptor` охватывает сервисную транзакцию, включая commit.
`ServiceErrors` преобразует ошибки JPA/JDBC в исключения приложения: нарушения
ограничений и блокировки — конфликт, неверные данные — ошибка ввода, отсутствие
соединения — недоступность БД (503), прочие ошибки БД — 500. Если JTA-адаптер
не сохранил SQL-причину сбоя commit, возвращается безопасный JSON с кодом 500;
тип ошибки не угадывается по тексту сообщения. SQLState не выходит
в HTTP-слой. Неизвестные ошибки логируются и получают безопасный ответ 500.

```bash
mvn test
mvn clean verify
```

Тесты проверяют статусы и формат ответов, валидацию полей, JSON, HTTP-заголовки,
преобразование SQLState, вложенные ошибки транзакций и JDBC batch, а также
сохранение исходной бизнес-ошибки. Реальное развёртывание требует работающей БД
и выполнения миграций по инструкции выше.
