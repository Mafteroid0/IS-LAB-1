Приложение построено на Spring Boot 3: Spring MVC (REST API), Spring Data JPA (Hibernate),
Spring Security (сессии), Bean Validation и Flyway. Фронтенд — статические файлы из
`src/main/resources/static`.

## Сборка и запуск

Требуются JDK 17+ и PostgreSQL. Maven устанавливать не обязательно, если он есть в IDE.
Все команды ниже выполняются из корня репозитория.

Настройте подключение к своей БД (значения по умолчанию указаны в `application.yml`):

```bash
export DB_HOST=localhost
export DB_PORT=5432
export DB_NAME=routes
export DB_USER=routes
export DB_PASSWORD='ваш-пароль'
export DB_SCHEMA=public
export DB_SSLMODE=disable
```

Для удалённого сервера задайте соответствующий `DB_SSLMODE` (например,
`verify-full` при настроенных сертификатах). База и роль должны существовать;
роль должна иметь права на создание объектов в указанной схеме.

```bash
mvn clean verify
java -jar target/routes.jar
```

Приложение: <http://localhost:8080/routes/>. Порт можно изменить параметром
`--server.port=8081`. Во время разработки удобно запускать `mvn spring-boot:run`.

Миграции Flyway применяются **автоматически при старте** приложения, до инициализации JPA:
Hibernate затем проверяет готовую схему (`spring.jpa.hibernate.ddl-auto=validate`).
Обычная сборка и тесты не подключаются к БД.

## Переход с существующей базы

Если таблицы уже созданы старым `db/schema.sql`, сначала сделайте резервную
копию и проверьте, что структура соответствует `V1__create_schema.sql`.
Для такой базы один раз выполните (переменные `DB_*` должны быть заданы):

```bash
mvn flyway:baseline -Dflyway.baselineVersion=1
mvn flyway:validate flyway:info
```

Baseline отмечает существующую схему как версию 1, без повторного создания таблиц
и удаления данных. Версия 2 устанавливает функции через `CREATE OR REPLACE`,
поэтому подходит и для базы, где старый `db/functions.sql` уже был выполнен; её применит
первый запуск приложения. Не выполняйте baseline для пустой или частично созданной схемы,
а также повторно после перехода на Flyway. Автоматический baseline отключён: непустая схема
без истории миграций требует этого явного шага, иначе приложение не запустится.
Команда `flyway:clean` отключена.

Применённые миграции не редактируйте: для изменения схемы или функций добавляйте
новые файлы `V3__description.sql`, `V4__description.sql` и т. д. При повторном
запуске уже применённые версии не исполняются заново, а их контрольные суммы
проверяются. Подробности: [Maven-плагин Flyway](https://documentation.red-gate.com/flyway/reference/usage/maven-goal),
[baseline](https://documentation.red-gate.com/flyway/reference/commands/baseline).

Хеши паролей сохраняют прежний формат PBKDF2, поэтому учётные записи, созданные до перехода
на Spring, продолжают работать.

## Безопасность

`SecurityConfig` закрывает весь `/api/**`, кроме `POST /api/auth/login` и
`POST /api/auth/register`; без входа API отвечает `401` в формате `{"message": "...", "fields": {}}`.
Сессия хранится в HTTP-only cookie и пересоздаётся при входе. Запросы API, изменяющие данные,
должны содержать заголовок `X-Requested-With: RouteLab` (иначе `403`), это защита от CSRF.

## Импорт маршрутов

Вкладка «Импорт» принимает JSON-файл (до 5 МБ, до 1000 записей) — массив маршрутов, вложенные объекты
задаются в той же записи:

```json
[
  {
    "name": "Маршрут 1",
    "coordinates": { "x": 1.5, "y": 2.5 },
    "from": { "x": 0, "y": 0, "z": 0, "name": "Старт" },
    "to":   { "x": 5, "y": 5, "z": 1, "name": "Финиш" },
    "distance": 10.5,
    "rating": 4
  }
]
```

Поле `from` необязательно. Ограничения те же, что при ручном вводе (название не пустое, расстояние больше 1,
рейтинг больше 0, конечные числа). Импорт выполняется одной транзакцией: при любой ошибке не создаётся ни один
объект. Результат каждой попытки попадает в историю импорта (id операции, статус, пользователь, число добавленных
маршрутов для успешных). Обычный пользователь видит только свои операции, администратор — все.
Администраторами считаются логины из `app.admins` (переменная окружения `APP_ADMINS`, по умолчанию `admin`):

```bash
export APP_ADMINS=admin,teacher
```

API: `POST /api/imports` (multipart, поле `file`), `GET /api/imports`.

## Ограничения уникальности

Проверяются в бизнес-логике (`UniquenessRules`), в БД не дублируются: название маршрута и название локации
(без учёта регистра и крайних пробелов), пара координат (x, y). Нарушение даёт `409`. Корректность при
параллельной работе обеспечивается глобальной блокировкой записи, см. [отчёт](docs/REPORT.md).

## Обработка ошибок и проверка

API сохраняет формат `{"message": "...", "fields": {}}`. Для неверных полей
`fields` содержит сообщения по именам полей. `ApiExceptionHandler`
(`@RestControllerAdvice`) преобразует исключения в ответы: неверный ввод — 400, отсутствие
объекта — 404, конфликт — 409, отсутствие авторизации — 401. Стандартные ошибки Spring MVC
(некорректный JSON, типы параметров, метод, формат данных) тоже возвращаются в этом формате,
заголовки вроде `Allow` сохраняются.

`ServiceErrors` преобразует ошибки JPA/JDBC/Spring в исключения приложения: нарушения
ограничений и блокировки — конфликт, неверные данные — ошибка ввода, отсутствие
соединения — недоступность БД (503), прочие ошибки БД — 500. Тип определяется по классам
исключений и SQLState, а не по тексту сообщений. SQLState и текст SQL не выходят
в HTTP-слой. Неизвестные ошибки логируются и получают безопасный ответ 500.
Ошибки, возникшие при commit транзакции, обрабатываются так же, как и ошибки внутри метода.

```bash
mvn test
mvn clean verify
```

Тесты проверяют статусы и формат ответов, валидацию полей и параметров, вход и выход,
защиту `X-Requested-With`, HTTP-заголовки, преобразование SQLState, вложенные ошибки
транзакций и JDBC batch. Реальный запуск требует работающей БД: миграции выполняются
самим приложением при старте.
